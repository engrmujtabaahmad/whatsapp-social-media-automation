# Project Title

Multi-Platform Conversational Publishing & Engagement Engine

## Overview

This project automates the flow of media content from WhatsApp directly to Facebook and Instagram, and handles intelligent, context-aware replies to comments received on those platforms — all built using n8n as the orchestration engine, without writing a traditional backend application.

The core idea: a user sends a photo or video via WhatsApp. Instead of a one-shot "photo + caption = post" pipeline, the bot now runs a **full guided conversation** — asking what to post, where to post it, whether a caption is wanted, and whether that caption should be written by the user or generated by AI directly from the media — before finally asking for confirmation and publishing. Separately, whenever someone comments on any of those posts, an AI model reads the comment, understands its context, and posts a unique, relevant reply — never a generic or repeated response.

Every completed post (successful or failed) is automatically logged as a row in a Google Sheet, and any workflow failure triggers an automatic email alert.

## Architecture Summary

The system consists of four independent n8n workflows, plus a supporting error-logging workflow:

1. **WhatsApp (Evolution API) → Social Media Publisher** — uses a self-hosted, unofficial WhatsApp automation layer
2. **WhatsApp (Meta Cloud API) → Conversational Social Media Publisher** — uses Meta's official, production-grade WhatsApp Business API, with a full interactive chatbot flow (this is the primary, actively developed route)
3. **Facebook Comment Handler** — listens for comments on Facebook posts and replies via AI
4. **Instagram Comment Handler** — listens for comments on Instagram posts and replies via AI
5. **Error Logger** — a small support workflow that catches failures from the main publishing workflow, logs them to Google Sheets, and emails an alert

Both WhatsApp routes were built in parallel: the Evolution API route was built first as a proof-of-concept and remains functional, while the Meta Cloud API route was subsequently built to provide a production-stable, Meta-sanctioned alternative that does not risk account bans, and was later extended into a full conversational chatbot with AI captioning and audit logging.

## Route 1: WhatsApp (Evolution API) → Facebook + Instagram

### Infrastructure
- Docker Desktop running three containers locally: n8n, evolution-api (v2.3.7), and a PostgreSQL database for Evolution API's session storage.
- Evolution API connects to a real WhatsApp number (923351657929) by scanning a QR code, effectively automating WhatsApp Web rather than using an official API.
- n8n itself runs with an internal Docker sub-stack for its own JavaScript "Code" node execution — this is n8n's Task Runner architecture (separate runners, sandbox-api, and sandbox-cert containers), which caused significant early debugging (documented below).

### Workflow: "WhatsApp Content Receiver"

Node chain:

```
Webhook (POST)
  → Edit Fields (extracts sender, pushName, messageType, isFromMe, caption, mimetype, messageKey from the raw Evolution API payload)
  → HTTP Request (POST to Evolution API's /chat/getBase64FromMediaMessage/{instance} endpoint, authenticated via an apikey header, to fetch the media as a base64 string)
  → Convert to File (converts the base64 string into a binary file object usable by downstream HTTP nodes)
  → HTTP Request "Upload to Cloudinary" (POST to https://api.cloudinary.com/v1_1/{cloud_name}/auto/upload, multipart/form-data, fields: file, upload_preset)
  → If node (branches based on messageType: image vs. video)
  → [Image branch] HTTP Request "Post Image FB" → HTTP Request "Create IG Container" → HTTP Request "Publish IG Post"
  → [Video branch] HTTP Request "Post Video FB" → HTTP Request "Create IG Video Container" → HTTP Request "Check Video Status" (polls Instagram's Graph API for status_code) → Wait node → HTTP Request "Publish IG Video"
```

### Key API Endpoints Used
- Facebook Photo Post: `POST https://graph.facebook.com/v21.0/{page-id}/photos` (multipart form: url, caption, access_token)
- Facebook Video Post: `POST https://graph.facebook.com/v21.0/{page-id}/videos` (multipart form: file_url, description, access_token)
- Instagram Container Creation: `POST https://graph.facebook.com/v21.0/{ig-business-account-id}/media` (fields: image_url or video_url + media_type: REELS for video, caption, access_token)
- Instagram Publish: `POST https://graph.facebook.com/v21.0/{ig-business-account-id}/media_publish` (fields: creation_id, access_token)

## Route 2: WhatsApp (Meta Cloud API, Official) → Conversational Publisher

Built as a production-stable alternative because the Evolution API approach technically violates WhatsApp's Terms of Service (it automates WhatsApp Web without official sanction) and carries a real risk of the number being banned. The Cloud API route uses Meta's officially sanctioned Business messaging product, and was later extended from a simple one-shot publisher into a **fully guided, stateful chatbot**.

### Setup
- A separate Meta Developer App was created: "OptimusFox Automation Tool" (App ID: `896759056633112`), linked to Business Portfolio "OptimusFoxPvtLtdProfessionals" (Business ID: `1117675637461236`). Kept separate from the Facebook/Instagram posting app to isolate WhatsApp Business permissions cleanly.
- A dedicated WhatsApp Business Account was registered: ID `1469073511704130`, with production phone number `+92 335 1657923`, fully verified.
- Since n8n is self-hosted on `localhost:5678`, and Meta requires a publicly reachable HTTPS callback URL for webhooks, ngrok was used to expose the local instance: static forwarding domain `backstage-spectacle-unclaimed.ngrok-free.dev`.

### Conversation Flow (Chatbot Logic)

Rather than requiring the user to send a photo/video with a pre-written caption in one message, the bot walks the user through a guided, menu-driven conversation:

1. **What to post** — Image or Video
2. **Media upload** — bot waits for the actual file matching the chosen type
3. **Where to post** — Facebook, Instagram, or Both
4. **Caption or not** — Yes / No
5. **If yes — who writes it** — the user themself, or AI
6. **If AI — source of direction**:
   - The user provides a style/prompt (e.g. "funny tone", "professional"), **or**
   - The AI is left to look at the photo/video itself and write a caption with no guidance
7. **AI caption review** — the generated caption (in English) is shown back to the user with three options:
   - Accept it as-is
   - Request changes (the user describes what to change, and the AI regenerates a revised caption incorporating that feedback — this can loop multiple times)
   - Discard it and write their own caption instead
8. **Final confirmation** — a summary (post type, caption, platform) is shown, and the user must explicitly confirm before anything is published
9. **Publish** — the workflow triggers Facebook/Instagram posting exactly as confirmed

All conversation prompts and system replies are in **English**.

### Session State Machine

Because each WhatsApp message arrives as an independent webhook call with no memory of prior messages, a persistent session is required to track where each user currently is in the conversation. This is implemented via a PostgreSQL table:

```sql
CREATE TABLE wa_sessions (
    phone_number    VARCHAR(20) PRIMARY KEY,
    current_state   VARCHAR(50) DEFAULT 'START',
    post_type       VARCHAR(10),
    media_id        VARCHAR(100),
    media_url       TEXT,
    platform        VARCHAR(20),
    wants_caption   BOOLEAN,
    caption_mode    VARCHAR(10),
    caption_text    TEXT,
    ai_prompt       TEXT,
    caption_edited  BOOLEAN DEFAULT false,
    last_reply      TEXT,
    updated_at      TIMESTAMP DEFAULT NOW()
);
```

On every incoming message, the workflow loads (or creates) the session row for that phone number, evaluates the current `current_state` against the user's input inside a central **State Machine** code node, computes the next state and the appropriate reply text, and writes the updated row back before replying — implementing a simple, explicit finite-state machine entirely in n8n, without any external framework.

States include: `START`, `AWAIT_TYPE`, `AWAIT_MEDIA`, `AWAIT_PLATFORM`, `AWAIT_CAPTION_YN`, `AWAIT_CAPTION_MODE`, `AWAIT_AI_SOURCE`, `AWAIT_AI_PROMPT`, `AI_GENERATING`, `AWAIT_AI_CONFIRM`, `AWAIT_AI_FEEDBACK`, `AWAIT_CAPTION_TEXT`, `AWAIT_CONFIRM`, `DONE`.

### AI Caption Generation (Vision-based)

When the user opts for an AI-written caption, the workflow:

1. Downloads the actual media binary from WhatsApp (via `Get Media Info` → `Download Media`)
2. Converts the binary to Base64 using n8n's binary-data helper (`this.helpers.getBinaryDataBuffer()`), since n8n's filesystem-mode binary storage does not expose raw Base64 directly
3. Builds a prompt (combining a fixed instruction template with the user's optional style guidance, or their edit feedback on a prior draft)
4. Sends the image/video (as inline Base64 data) plus the prompt to Google Gemini (`gemini-3.6-flash`) via its `generateContent` endpoint, requesting a short, natural, emoji-appropriate English caption
5. Returns the generated caption to the user for review, with the accept / request-changes / write-my-own options described above

The "request changes" path re-invokes the same Gemini call with an updated prompt that includes both the previous caption and the user's specific feedback, allowing iterative refinement before the final post.

### Automated Logging to Google Sheets

Every completed publish attempt (successful or failed) is recorded as a row in a Google Sheet, with the following columns:

| Column | Description |
|---|---|
| Date & Time | Timestamp of the execution |
| PostType | `image` or `video` |
| HasCaption | Whether a caption was included |
| CaptionBy | `Self`, `AI`, or `N/A` |
| Edited | Whether the AI caption was revised via feedback before posting |
| Platform | `Only Facebook`, `Only Instagram`, or `Facebook/Instagram` |
| PostLink | Link(s) to the published post(s) |
| ExecutionID | The n8n execution ID, for cross-referencing with execution logs |
| Status | `Success` or `Failed` |
| Error | The error message, if the execution failed |

Successful rows are written by a `Prepare Log Row` node (fed from all four possible posting-completion nodes: Post Image FB, Post Video FB, Publish IG Post, Publish IG Video) followed by a Google Sheets "Append Row" node.

### Automated Failure Alerts

A separate, minimal workflow — **"Error Logger"** — is configured as this workflow's **Error Workflow** (set under Workflow Settings). It consists of an `Error Trigger` node feeding two parallel branches:
1. A Google Sheets "Append Row" node, writing a `Failed` row with the execution ID and error message to the same log sheet
2. A Gmail "Send" node, emailing a failure alert containing the execution ID, workflow name, error message, and timestamp

This means any failure anywhere in the main publishing workflow — a bad API response, an expired token, a malformed request — is automatically captured, logged, and notified, with zero manual monitoring required.

### Node chain (high level)

```
Webhook (GET) — handles Meta's one-time verification handshake
  → Respond to Webhook (returns hub.challenge)

Webhook (POST, same path) — receives actual incoming message events
  → Code node (parses entry[0].changes[0].value; extracts sender, messageType, mediaId, caption, and — for button/list replies — buttonId and textBody; returns [] early for status-update-only payloads)
  → Get Session (Postgres SELECT on phone_number)
  → State Machine (central conversation logic, described above)
  → Check AI Generate (branches into the AI captioning sub-flow when applicable)
  → Upsert Session (Postgres INSERT ... ON CONFLICT UPDATE, persists the new state)
  → Send WhatsApp Reply (POST to the Cloud API's /messages endpoint with the computed reply text)
  → [on final confirmation] Prepare Post Data → media download/upload → platform-specific Facebook/Instagram posting → Prepare Log Row → Append Row in Sheet
```

### Access Token Strategy

Initially, a temporary token (~24-hour expiry) generated from the App's "API Setup" page was used for testing. For production stability, this was replaced with a permanent System User token:
- A System User ("OptimusFox Automation Bot") was created in Meta Business Settings under the relevant Business Portfolio, assigned the "Admin" role.
- The System User was granted Full Access (Manage app) to the "OptimusFox Automation Tool" App, and Full Access to the WhatsApp Business Account.
- A new token was generated for this System User with Token Expiration set to "Never", scoped with `whatsapp_business_messaging` and `whatsapp_business_management` permissions.
- This permanent token replaced the temporary one across all relevant HTTP Request nodes.

## Route 3: Facebook Comment Auto-Reply

### Workflow: "Facebook Comment Handler"

```
Webhook (GET) — Meta verification handshake
  → Respond to Webhook (returns hub.challenge)

Webhook (POST, same path) — receives feed change events
  → Code node — filters for genuine new comments (value.item === "comment" and value.verb === "add"), extracting comment_id, post_id, comment_text
  → HTTP Request "Get Comment Sender" (GET /{comment_id}?fields=from&access_token=... — required because Facebook's "feed" webhook field does not include the commenter's user ID inline)
  → If node — compares the commenter ID against the Page's own ID; matches are dropped to prevent an infinite reply loop
  → Google Gemini node (model: gemini-3.6-flash) — generates a short, natural, contextually relevant reply matching the tone of the original comment
  → HTTP Request — POST /{comment_id}/comments (fields: message, access_token) to publish the AI-generated reply
```

**Note on AI provider:** OpenAI's GPT API was the original plan, but was abandoned after hitting a billing/no-credits error. Google Gemini (free tier) was substituted successfully with no functional loss.

### Webhook Subscription Configuration (Critical Detail)

Meta's Webhooks product for the "Page" object exposes dozens of subscribable fields. The `feed` field specifically must be toggled to **Subscribed** for comment events to be delivered at all — missing this initially caused a completely silent failure (no executions, no errors). Additionally, the Page itself had to be explicitly linked to the App via `POST /{page-id}/subscribed_apps?subscribed_fields=feed` in Graph API Explorer, which required the `pages_manage_metadata` permission.

## Route 4: Instagram Comment Auto-Reply

### Workflow: "Instagram Comment Handler"

Follows the same architectural pattern as the Facebook handler, with two key differences:
- **Reply endpoint:** Instagram uses `POST /{comment_id}/replies` (not `/comments`, as Facebook does).
- **Sender identification:** Instagram's comments webhook payload includes the commenter's ID directly (`value.from.id`) in the initial event, so the extra "Get Comment Sender" lookup step used in the Facebook workflow is unnecessary here.

Instagram Business Account ID `17841433751186422` is shared with the posting workflows, as it is the same account.

## Workflow Canvas Organization

To keep the main "WhatsApp Cloud API Receiver" workflow readable for anyone reviewing it, the canvas is organized into seven labeled, color-coded sticky-note sections:

1. **Webhook Verification** — Meta's GET handshake
2. **Incoming Message Handler** — receives messages, loads session, runs the state machine
3. **AI Caption Generation** — media download, Base64 conversion, Gemini call, result formatting
4. **Session Save & User Reply** — persists state, sends the WhatsApp reply
5. **Post Preparation** — fetches final media, uploads to Cloudinary, determines routing
6. **Facebook & Instagram Posting** — all platform-specific publishing logic, including Instagram's asynchronous video processing poll-loop
7. **Logging** — writes the completed post's details to Google Sheets

Every node has been renamed from n8n's generic defaults (e.g. `If`, `HTTP Request`, `HTTP Request1`) to a descriptive name reflecting its actual function (e.g. `Check Media Type`, `Get Media URL from WhatsApp`, `Check IG Video Status`).

## Errors Encountered and Resolutions (Full Debugging Log)

This section documents every significant failure encountered during development, in chronological order, to demonstrate the debugging process.

### 1. n8n Task Runner Timeout ("Task request timed out")
**Symptom:** Every execution of any JavaScript "Code" node failed after a 60-second wait with a generic timeout error.
**Root cause:** n8n's Docker deployment includes a separate internal container architecture (runners, sandbox-runner, sandbox-api, sandbox-cert) for isolating JavaScript execution. Logs revealed "Task broker is down, launcher will try to reconnect" — a networking failure between the main n8n container and its runner sidecar.
**Resolution:** Interim — replaced Code nodes with Edit Fields (Set) nodes, which execute inside the core n8n process. Permanent — after the Docker stack settled/restarted correctly, Code nodes were successfully reintroduced.

### 2. Cloudinary "Bad request - Empty file"
**Symptom:** The Cloudinary upload step reported the file parameter as empty.
**Root cause:** The Code node's Base64 extraction logic never referenced the correct nested payload path, so the field was always undefined.
**Resolution:** Corrected the extraction path with a fallback check across possible payload shapes.

### 3. Instagram "Media download has failed" / aspect ratio rejection
**Symptom:** Facebook photo posting succeeded, but the same image was rejected when creating an Instagram media container.
**Root cause:** The source image's aspect ratio (e.g. 899×1599 ≈ 0.56, or 1006×1512 ≈ 0.665) fell outside Instagram's accepted range (0.8 to 1.91:1). Facebook's Photos API has no such restriction.
**Resolution:** Applied an on-the-fly Cloudinary URL transformation (`w_1080,h_1350,c_fill,g_auto,q_auto`) inserted into the delivery URL, automatically resizing/cropping the image into Instagram's accepted aspect ratio before submission — no manual editing required.

### 4. Instagram Container Fetch Timing Failure
**Symptom:** Even with a correctly transformed, publicly-accessible Cloudinary URL, Instagram intermittently rejected brand-new uploads with "Only photo or video can be accepted as media type," while the identical URL worked fine when tested manually moments later.
**Root cause:** A dynamically-generated Cloudinary transformation is created on-the-fly on first request; Facebook's media fetcher sometimes attempted to retrieve the transformed asset before Cloudinary had finished generating and caching it.
**Resolution:** Inserted a `Wait` node (3 seconds) between the Cloudinary upload/transform step and the Instagram container-creation call, giving Cloudinary's CDN time to fully propagate the derived asset before Facebook fetches it.

### 5. Instagram video publish "Media ID is not available"
**Symptom:** Instagram video container creation succeeded, but the immediate "publish" call failed.
**Root cause:** Instagram processes uploaded video asynchronously; a fixed-duration Wait node was sometimes insufficient for longer videos, so the publish call fired before transcoding finished.
**Resolution:** Introduced an explicit status-polling step (`GET /{container-id}?fields=status_code`) checked in a loop before publishing, ensuring the video is confirmed `FINISHED` before the publish call is made.

### 6. Facebook OAuth "Invalid OAuth access token — Cannot parse access token"
**Symptom:** A previously working Facebook posting node suddenly failed.
**Root cause:** Hidden formatting artifacts (line breaks/invisible characters) were introduced into the access token when pasted into the node's parameter field.
**Resolution:** Cleared the field entirely and re-pasted the token as a single unbroken line.

### 7. Facebook/Instagram Long-Lived Token Expiring Prematurely
**Symptom:** All Facebook/Instagram-related nodes across multiple workflows began failing simultaneously with "Error validating access token: Session has expired".
**Root cause:** The previously generated 60-day long-lived Page Access Token had expired (tokens generated through the interactive Graph API Explorer flow are more prone to premature invalidation than System User tokens).
**Resolution:** Regenerated a fresh Page Access Token, exchanged it for a new long-lived token, and propagated it across every affected node.

### 8. WhatsApp Cloud API — Zero Executions Despite Correct Setup
**Symptom:** Webhook verification succeeded, the callback URL was reachable, yet sending real WhatsApp messages triggered no n8n executions.
**Root cause:** On Meta's Webhook Configuration page, the `messages` field — the one carrying incoming message events — was left Unsubscribed among dozens of other irrelevant fields.
**Resolution:** Explicitly toggled `messages` to Subscribed; executions began firing correctly.

### 9. IF Node Silently Routing Videos to the Image Branch
**Symptom:** Videos were incorrectly processed through the image-posting branch, causing Facebook to reject the file.
**Root cause:** The IF node's condition used the `.item` accessor to reference a prior node's output. With several HTTP Request nodes sitting between the source node and the IF node, n8n's paired-item tracking broke silently.
**Resolution:** Replaced `.item` with `.first()`, retrieving the first output item directly by node reference rather than relying on paired-item chain tracking.

### 10. Gemini API "Too Many Requests" (Quota Exceeded)
**Symptom:** AI reply/caption generation intermittently failed during rapid, repeated manual testing.
**Root cause:** Google Gemini's free tier enforces a strict per-minute request quota, exceeded by frequent back-to-back test requests.
**Resolution:** Spaced out test requests by 1–2 minutes; additionally enabled **Retry On Fail** (3 attempts, 2-second delay) on the Gemini HTTP Request node to automatically recover from transient "Service unavailable — high demand" errors without manual intervention.

### 11. Binary Data Returning a File Reference Instead of Actual Base64
**Symptom:** The Gemini vision API rejected the request with "Invalid value at 'contents[0].parts[1].inline_data.data' — Base64 decoding failed for 'filesystem-v2'."
**Root cause:** n8n, when configured to store binary data on disk ("filesystem" mode) rather than in memory, returns an internal file-reference string (not the actual file content) when a binary field is read directly.
**Resolution:** Used n8n's `this.helpers.getBinaryDataBuffer()` helper inside the Code node to explicitly read the file's actual contents from disk before converting to Base64, rather than reading the binary property directly.

### 12. AI Confirmation Reply Not Reaching WhatsApp
**Symptom:** After AI caption generation completed successfully (confirmed via execution logs), the WhatsApp reply the user received was always the earlier "generating..." placeholder message rather than the actual caption confirmation prompt.
**Root cause:** The "Send WhatsApp Reply" node's message body referenced a specific upstream node (`State Machine`) by name using `$('State Machine')`, which only reflects that node's own state, not the state produced later by the AI-generation branch (`Format AI Result`) — and cross-branch node references are unreliable when no direct graph connection exists between them.
**Resolution:** Added a `last_reply` column to the session table; the Upsert Session node now persists whichever reply text was actually computed for that execution (regardless of branch), and the WhatsApp reply node reads `{{ $json.last_reply }}` from its direct input instead of reaching across branches.

### 13. Postgres Node Crash: "Cannot read properties of null (reading 'includes')"
**Symptom:** The Upsert Session node failed intermittently with a null-property error.
**Root cause:** A dynamic expression (`{{ $json.aiPrompt }}`) had been mistakenly placed in the node's "Output Columns" option field (which expects a static column-name list, not a value expression) rather than in the "Values to Send" mapping — causing a crash whenever `aiPrompt` was null.
**Resolution:** Removed the expression from Output Columns and added it correctly as a mapped field under Values to Send.

## Setup Notes for Reviewers

Before importing and running these workflow JSON files, the following placeholders must be replaced with your own credentials — they have been stripped from the exported files for security:

- `YOUR_WHATSAPP_ACCESS_TOKEN` — Meta WhatsApp Cloud API / Graph API access token (used across all Facebook/Instagram/WhatsApp HTTP Request nodes)
- `YOUR_GEMINI_API_KEY` — Google Gemini API key (used in the `x-goog-api-key` header of the AI caption/reply nodes)
- **Postgres credentials** — must be configured separately inside n8n's credential manager; they are never included in the exported JSON
- **Google Sheets credentials** — must be authorized separately inside n8n; connect to your own copy of the log spreadsheet
- **Cloudinary** — cloud name and unsigned upload preset should be replaced with your own account's values

A demo video (3–5 minutes) and a separate `.env`-style credentials file were prepared for submission alongside this repository, per the project brief's submission requirements.
